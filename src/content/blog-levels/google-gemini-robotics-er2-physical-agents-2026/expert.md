Google が2026年7月30日に Gemini API のリリースノートで public preview として示した **Gemini Robotics ER 2** は、Gemini API の利用領域をロボティクスと Physical AI へ広げる更新である。DeepMind の発表とモデルカードを合わせて読むと、ER 2 は Gemini 3.5 Flash を基盤に、動画、画像、テキストを使ってロボットの作業状況を推論する embodied reasoning model として位置づけられる。

この更新は、Google のエージェント基盤戦略の一部として見る必要がある。[Gemini API Managed Agents](/blog/google-gemini-api-managed-agents-2026/) は、隔離環境、ツール、ファイル状態を持つソフトウェア agent 実行基盤だった。[Gemini Interactions API GA](/blog/google-gemini-interactions-api-ga-2026/) は、会話や状態を含むアプリ側の agent interaction を扱う更新だった。ER 2 は、その延長にありながら、入力が現場映像とロボット状態へ移るため、失敗時の責任、個人データ、物理安全、遅延の扱いが一段重くなる。

日本企業にとっては、製造業、物流、インフラ保守、建設、小売バックヤード、ロボットSI、組込み機器開発の文脈で重要だ。ただし、ER 2 を「Googleが出したロボットAI」と雑に読むと危ない。preview段階で本番自律制御に直行するのではなく、映像理解、作業進捗分類、失敗場面検出、遠隔操作支援、人間レビュー付きの手順確認から評価するのが現実的である。

## 事実: ER 2は時間軸を持つロボット理解を狙う

Google AI for Developers のリリースノートでは、Gemini Robotics ER 2 が2026年7月30日に public preview として追加されたことが示されている。同時に、Gemini Robotics ER 1.6 preview は2026年8月31日に廃止予定とされている。すでにER 1.6を検証していたチームにとっては、新モデルの性能確認だけでなく、評価セット、プロンプト、動画入力、レスポンス処理、ログの比較が必要になる。

DeepMind の発表が強調するのは temporal intelligence である。ロボットにとって、静止画の理解は十分条件ではない。物体があることを理解するだけでなく、どの動作が終わり、どの動作が失敗し、次にどの選択肢が安全かを時間の流れから判断する必要がある。ER 2 は、動画内の作業進捗や重要な瞬間を見つける評価で改善を示したと説明されている。

モデルカードでは、ER 2 はロボティクス向けの vision-language model として、入力文脈、出力、制約、安全評価を整理している。ここで読み取るべきなのは、ベンチマークの数字だけではない。モデルカードが、想定用途、制限、個人データ、安全性、ロボット動作に関わるリスクを別枠で扱っていること自体が重要である。Physical AIでは、モデルの応答品質と現場安全を同じ評価表に入れなければならない。

## 分析: Gemini APIのagent基盤が現場データへ伸びた

ここからは分析だ。ER 2 は、Google が「agent」をソフトウェアの自動化だけでなく、現実世界の観測と行動支援へ広げていることを示す。Gemini API は、モデル、file、tool、interaction、managed execution といった部品を増やしてきた。ER 2 はそこへロボティクス用の embodied reasoning を加える。

ただし、現場データはソフトウェアログより扱いが難しい。ソースコードやドキュメントの入力なら、機密管理と権限で多くを整理できる。一方、工場や倉庫の映像には、個人、設備、作業手順、顧客資産、サプライチェーン情報が一緒に映る。さらに、AIの出力がロボット動作に影響するなら、誤答は画面上の誤説明ではなく、物理的な事故やライン停止につながる可能性がある。

この意味で、ER 2 の導入評価は [Gemini 3.5 Flashのstable運用](/blog/google-gemini-35-flash-api-stable-agents-2026/) より厳密であるべきだ。モデルIDを固定する、previewとstableを分ける、評価セットを作るという基本は同じだが、ロボティクスでは現場の境界条件を評価セットへ入れる必要がある。照明、遮蔽、反射、手袋、制服、同型部品、騒音、通信断、緊急停止、作業者の割り込みを含めない評価は、本番判断に使いにくい。

## 評価設計: 正答率より先に失敗モードを列挙する

日本の導入チームが最初にやるべきことは、ER 2 のデモを触ることではなく、失敗モードの一覧化である。たとえば倉庫ピッキング支援なら、対象商品を取り違える、棚番を読み違える、作業者が途中で別作業へ移る、カメラが揺れる、箱が重なって見えない、バーコードと現物が不一致になる、といったケースがある。

設備点検なら、正常と異常の差が小さい、汚れと損傷を間違える、メーター表示が反射する、点検順序が現場都合で前後する、過去の画像と比較しないと判断できない、という失敗がある。ロボットアームなら、把持対象がずれる、柔らかい物体が変形する、人の手が近づく、治具が動く、停止後の復帰手順が分からない、という問題が出る。

ER 2 を評価するなら、こうした失敗モードをテストケース化する。出力は単純な正誤だけでは足りない。判断根拠、タイムスタンプ、信頼度に相当する説明、停止すべき条件、再試行すべき条件、人間へ確認を返す条件を分けて記録する。moment finding のような能力を使うなら、「何秒の範囲を正解とするか」「作業者の個人差をどう扱うか」「同じ作業の別手順をどう認めるか」を先に決める必要がある。

## アーキテクチャ: クラウドAPI、エッジ、既存制御を分ける

ER 2 は Gemini API から使えることが大きな入口だが、現場システム全体をクラウドAPIだけで考えるべきではない。ロボット制御には既存のPLC、ROS、専用コントローラ、安全回路、監視カメラ、MES、WMS、保全システムがある。Gemini API はその一部であり、最終制御層ではない。

現実的な構成は、まずAIを助言層に置くことだ。カメラ映像や作業ログをもとに、作業進捗、異常候補、確認ポイントを出す。人間または既存システムが承認し、ロボットAPIや現場端末へ反映する。自律制御へ進む場合でも、AIの出力を直接モーター命令へつなぐのではなく、安全PLCやローカル制御の制約内で動かす。

この設計は、[PFNのPLaMo-VL](/blog/pfn-plamo-vl-physical-ai-2026/) と [JR東海とPFNのAIエッジデータセンター構想](/blog/jr-central-pfn-ai-edge-datacenter-2026/) の文脈とも接続する。PLaMo-VL は国産VLMとして、現場デバイスや日本語視覚理解に近い論点を持つ。JR東海とPFNの構想は、現場近くの推論基盤が必要になる理由を示している。ER 2 は強力なクラウドAPI側の候補だが、国内現場ではエッジ推論、閉域網、ローカル安全制御との役割分担を必ず検討したい。

## データガバナンス: 映像はログより重い

ER 2 のPoCで見落としやすいのは、映像データの重さである。開発チームは、プロンプトやAPIログには敏感でも、カメラ映像を「検証用素材」として軽く扱いがちだ。しかし現場映像には、顔、服装、名札、作業姿勢、設備配置、製造ノウハウ、取引先情報が映り込む。

そのため、PoC開始前に少なくとも次を決める必要がある。撮影範囲、録画の有無、保存期間、アクセス権、外部送信の範囲、顔や名札のマスキング、個人への通知、委託先との契約、削除手順、事故時の調査ログである。Google のドキュメントやモデルカードが個人データと安全に触れているのは、ロボティクスではこの部分が避けられないからだ。

日本企業では、現場映像を海外クラウドへ送ること自体に社内審査が必要になる場合がある。これを後回しにすると、技術評価で良い結果が出ても本番化できない。最初から匿名化されたサンプル、実験環境、顔ぼかし済み映像、合成データ、外部送信不可エリアの切り分けを用意したほうがよい。

## 導入ロードマップ: 3段階で扱う

第1段階は、説明と検索である。ER 2 に現場映像を見せ、作業進捗、失敗場面、確認ポイントを説明させる。ここではロボット制御へつながず、評価者が回答を採点する。目的は、モデルが何を見ているか、どの条件で外すかを知ることだ。

第2段階は、人間承認付きの支援である。作業者や監督者に対して、次の確認、手順漏れ、リスク候補を提示する。現場端末、チャット、管理画面へ返す場合も、承認と上書きの導線を用意する。AIが「分からない」と返せる設計にして、無理に判断させない。

第3段階は、既存制御との限定連携である。たとえば、低リスクなデモラインで、AIが検出した進捗をWMSや保全台帳へ記録する。ロボット動作へ近づける場合でも、速度、可動範囲、停止条件、再開条件はローカル制御側で制限する。AIは候補を出し、安全制御は既存システムが担う、という分担を崩さない。

## まとめ

Gemini Robotics ER 2 は、Gemini APIのエージェント基盤が物理世界の観測と行動支援へ伸びたことを示す重要なpreviewである。時間軸を含む映像理解、作業進捗、moment finding、低遅延ストリーミング、安全評価は、日本の製造、物流、設備保全、ロボットSIにとって検証価値が高い。

一方で、本番導入の焦点はモデル性能だけではない。映像データ、個人情報、現場安全、エッジとクラウドの分担、既存制御、停止条件、人間レビュー、失敗モードの評価がそろって初めて、PoCの結果を経営や現場責任者へ説明できる。ER 2 はPhysical AIの有力な入口だが、現場の安全設計と評価設計を省略できる近道ではない。
